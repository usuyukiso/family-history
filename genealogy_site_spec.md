# Спецификация сайта генеалогической книги

**Статус:** начальная техническая спецификация  
**Версия:** 0.1  
**Язык документа:** русский  
**Целевая платформа:** GitHub + MkDocs Material + GitHub Pages  
**Назначение:** публичная онлайн-книга об умерших родственниках с биографиями, фотографиями, документами, родословными связями и проверяемыми источниками.

---

## 1. Цели проекта

Создать статический сайт, который:

- представляет генеалогическое исследование в виде читаемой онлайн-книги;
- содержит отдельную страницу для каждой персоны;
- связывает персон между собой и с семейными ветвями;
- классифицирует источники и документы по единой системе идентификаторов;
- позволяет переходить по внутренним и внешним гиперссылкам;
- различает подтверждённые факты, противоречивые сведения и гипотезы;
- поддерживает фотографии, сканы, PDF и ссылки на внешние архивы;
- хранит исходные тексты в Markdown и конфигурацию в Git;
- публикуется автоматически после отправки изменений в GitHub;
- не требует собственного сервера, базы данных или backend для первой версии.

### 1.1. Не входит в первую версию

- аналитика посетителей и трекинг;
- пользовательские аккаунты, комментарии и формы;
- база данных и серверная логика;
- автоматическая генерация полноценного интерактивного родословного дерева;
- публикация закрытых или конфиденциальных семейных материалов.

## 2. Технологический стек

| Компонент | Назначение |
|---|---|
| Git | История изменений, ветвление и контроль версий |
| GitHub repository | Хранение исходников проекта |
| Python + MkDocs | Сборка сайта из Markdown |
| Material for MkDocs | Тема, навигация, поиск и оформление |
| GitHub Actions | Автоматическая сборка и публикация |
| GitHub Pages | Бесплатный статический хостинг для публичного сайта |
| Markdown | Биографии, страницы источников и главы |
| YAML front matter | Структурированные метаданные в начале Markdown-файлов |
| CSS (при необходимости) | Дополнительные стили сайта |

### 2.1. Основной принцип

Исходными данными являются Markdown-файлы, изображения, документы и конфигурация в репозитории. MkDocs собирает из них статический сайт: HTML, CSS, JavaScript и копии ресурсов.

Файл `mkdocs.yml` управляет настройками сборки, но не является страницей сайта. После публикации посетители видят собранный сайт.

### 2.2. Версии и зависимости

- Зафиксировать рабочую версию Python и зависимости проекта.
- Добавить `requirements.txt` с `mkdocs-material`.
- Обновлять зависимости осознанно, проверяя локальную сборку перед публикацией.
- Не устанавливать зависимости «последней версии» в production без проверки.

Пример `requirements.txt`:

```text
mkdocs-material
```

Для воспроизводимых сборок позднее следует зафиксировать проверенные версии зависимостей.

## 5. Система идентификаторов

### 5.1. Общие правила

- Идентификатор уникален и не меняется после назначения.
- Не переиспользовать ID удалённой или объединённой записи.
- ID не должен кодировать изменяемые сведения, например фамилию или дату рождения.
- Внутренние ссылки следует строить на страницы, а в метаданных хранить ID.
- Последовательные номера выдаются вручную либо скриптом; перед добавлением новой записи нужно проверять уникальность.
- Для ссылок в тексте использовать понятные названия, а не голые ID, кроме случаев, где ID нужен для точной идентификации.

### 5.2. Персоны и семейные группы

| Префикс | Тип | Пример |
|---|---|---|
| `P` | Персона | `P1000` |
| `FAM` | Семья / семейная группа | `FAM1000` |
| `EV` | Событие | `EV1000` |
| `PLC` | Место | `PLC1000` |

Персона — конкретный человек. Семейная группа — связь между партнёрами/супругами и, при необходимости, детьми. Событие — отдельный факт с датой и местом, например брак или миграция. Место — населённый пункт, усадьба, кладбище или другой географический объект.

Для небольшой первой версии страницы событий и мест могут быть простыми разделами внутри биографий; отдельные записи полезны, когда объектов становится много.

### 5.3. Источники

Предложенные пользователем префиксы сохраняются:

| Префикс | Тип источника | Пример |
|---|---|---|
| `F` | Фото / фотография | `F1000` |
| `D` | Документ или цифровая копия документа (скан, PDF) | `D1000` |
| `A` | Архивный источник, архивная запись или ссылка на архивный каталог | `A1000` |
| `B` | Книга / опубликованное издание | `B1000` |
| `W` | Веб-сайт или отдельная веб-страница | `W1000` |
| `N` | Газета, журнал или периодическая публикация | `N1000` |
| `L` | Письмо или другая личная переписка | `L1000` |
| `I` | Интервью, устное свидетельство, семейное воспоминание | `I1000` |
| `M` | Карта, план или географический материал | `M1000` |
| `DB` | Внешняя генеалогическая или архивная база данных | `DB1000` |
| `V` | Видео- или аудиозапись | `V1000` |
| `O` | Официальная публикация или отчёт, не отнесённые к книге/архивной записи | `O1000` |

**Важное различие между `D` и `A`:**

- `D` описывает конкретный документ или файл: скан свидетельства, PDF, фотографию страницы регистра.
- `A` описывает архивный источник или запись в архивном каталоге: учреждение, фонд, опись, дело, лист, архивную карточку и ссылку на цифровой оригинал.
- Один `A` может ссылаться на несколько `D`, если в архиве имеется несколько цифровых изображений одного дела.
- Если документ существует только как локальный скан и архивные реквизиты неизвестны, допустимо создать `D` и явно указать, что происхождение требует проверки.
- Если внешняя архивная страница сама содержит цифровую копию документа, можно завести `A` и связать её с `D`, когда это полезно.

**Фото и документы могут быть как локальными файлами, так и внешними ресурсами.** Тип записи определяется ролью материала, а не только местом хранения. Например, `F1000` описывает фотографию, а файл изображения хранится в `docs/assets/images/`.

### 5.4. Идентификаторы и имена файлов

Рекомендуемый формат имени файла:

`<ID>-<short-description>.md`

Примеры:

- `P1000-ivan-petrov.md`
- `F1000-ivan-petrov-portrait.md`
- `D1000-birth-record.md`
- `A1000-parish-register.md`

ID в имени файла облегчает поиск и уменьшает вероятность путаницы. После публикации желательно не переименовывать страницы без необходимости, поскольку внешние ссылки могут на них указывать.

## 6. Правила работы с фактами и достоверностью

Каждое существенное утверждение о персоне по возможности связывается с источником. Не следует создавать впечатление, что все сведения одинаково достоверны.

Рекомендуемые статусы:

- **Подтверждено** — найден источник, непосредственно подтверждающий утверждение.
- **Вероятно** — есть косвенные доказательства, но окончательное подтверждение отсутствует.
- **Предположение** — рабочая гипотеза исследователя.
- **Противоречие** — разные источники содержат несовместимые сведения.
- **Не установлено** — данных пока недостаточно.

Правила:

1. Сохранять оригинальное написание имён в источнике, если оно отличается от принятого в биографии.
2. Не считать совпадение имени и фамилии достаточным доказательством идентичности человека.
3. Для дат с неопределённостью явно указывать приблизительность: например, «около 1885 года».
4. Указывать, какой источник подтверждает конкретный факт, а не просто приводить общий список литературы.
5. Отмечать противоречащие источники и объяснять, почему выбран тот или иной вариант.
6. Различать дату события, дату создания документа и дату обращения к веб-странице.
7. Не публиковать непроверенные предположения как установленные факты.

## 13. Прочие типы источников

Рекомендуемые дополнительные типы:

- `N` — газета или периодическое издание: некролог, объявление, новость.
- `L` — личная переписка: письма, открытки, дневниковые записи.
- `I` — устное свидетельство: интервью с родственником, семейное воспоминание. Следует фиксировать дату интервью и автора свидетельства.
- `M` — карта, план населённого пункта, кадастровый или исторический план.
- `DB` — генеалогическая база или внешний каталог, в котором есть отдельная запись о человеке.
- `V` — видео- или аудиозапись, например оцифрованная запись интервью.
- `O` — официальный отчёт, справочник или публикация, которая не подходит к остальным категориям.

Не следует создавать новый тип для каждого редкого случая. Если материал можно разумно отнести к существующему типу, нужно использовать существующий префикс.

### 13.1. Первичный и вторичный источник

Тип материала и качество доказательства — разные характеристики. Например, архивная запись может быть первичным источником, а книга исследователя — вторичным. Это лучше фиксировать отдельным полем, например:

```yaml
evidence_kind: primary
```

Возможные значения: `primary`, `secondary`, `tertiary`, `unknown`. Это поле не должно автоматически определяться только по префиксу источника.

## 16. Автоматическая публикация через GitHub Actions

Рекомендуется публиковать сайт через GitHub Actions, чтобы сборка проверялась при каждом изменении и результат публиковался только после успешной сборки.

Пример workflow `.github/workflows/deploy.yml`:

```yaml
name: Deploy MkDocs site

on:
  push:
    branches:
      - main
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.x"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Build site
        run: mkdocs build --strict

      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: site/

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

Примечания:

- Пример использует версии GitHub Actions, указанные в документации на момент составления спецификации; перед внедрением следует проверить актуальные рекомендации GitHub.
- В настройках репозитория открыть **Settings → Pages** и выбрать **GitHub Actions** в качестве источника публикации.
- Проверить разрешения workflow и настройки Pages.
- `mkdocs build --strict` останавливает сборку при предупреждениях, включая многие проблемы навигации и ссылок; перед включением строгого режима нужно устранить предупреждения.
- Не хранить секреты, пароли и приватные данные в репозитории.

## 17. Изображения и документы

### 17.1. Фотографии

- Для отображения на сайте использовать оптимизированные JPEG или WebP.
- Оригиналы в высоком разрешении хранить отдельно, если они слишком велики для репозитория.
- Применять понятные имена файлов, желательно с ID источника или персоны.
- Указывать описание изображения и альтернативный текст.
- Не загружать один и тот же большой файл в несколько каталогов без необходимости.

Пример имени:

`docs/assets/images/people/F1000-ivan-petrov.jpg`

### 17.2. Документы

- PDF и сканы хранить в `docs/assets/documents/`.
- Использовать отдельную страницу описания документа с ID `D...`.
- Если есть архивные реквизиты, связать документ с источником `A...`.
- Большие коллекции сканов не включать в сайт автоматически без оценки размера.
- Не рассчитывать на то, что удаление файла из текущей версии репозитория удалит его из истории Git.

### 17.3. Ограничения GitHub Pages

Перед публикацией учитывать действующие ограничения GitHub Pages: опубликованный сайт ограничен по размеру, а для репозитория рекомендуются умеренные размеры. Проверять актуальные значения в официальной документации GitHub, поскольку лимиты и рекомендации могут изменяться.

### 17.4. Резервное копирование

GitHub не должен быть единственным местом хранения оригиналов. Рекомендуется:

- локальная копия репозитория;
- отдельная резервная копия исходных фотографий и документов;
- периодическая проверка возможности восстановления.

## 18. Ссылки, поиск и качество

### 18.1. Внутренние ссылки

- Все связи между персонами оформлять гиперссылками.
- Все упомянутые источники должны вести на их страницы, если такие страницы существуют.
- При переименовании или перемещении файлов обновлять внутренние ссылки.
- Проверять сборку перед публикацией.

### 18.2. Внешние ссылки

Для внешнего источника хранить:

- URL;
- название страницы или записи;
- автора/учреждение, если известны;
- дату публикации, если известна;
- дату обращения;
- архивные реквизиты или идентификатор записи, если применимо;
- краткое описание того, что именно подтверждает ссылка.

Внешние сайты могут менять адреса или удалять материалы. По возможности сохранять библиографические и архивные реквизиты, чтобы источник можно было найти повторно.

### 18.3. Поиск

Встроенный поиск MkDocs Material должен находить текст на опубликованных страницах. Для упрощения поиска следует:

- использовать единообразное написание имён;
- добавлять варианты написания и транслитерации;
- делать алфавитный указатель персон;
- использовать единые термины и категории.

Поиск по произвольным метаданным YAML не следует считать гарантированным без проверки; при необходимости ID и альтернативные имена можно выводить в видимом тексте страницы.

## 19. Конфиденциальность, права и публикация

Проект предполагается публичным и посвящён преимущественно умершим персонам. Тем не менее перед публикацией необходимо учитывать:

- персональные данные живых родственников, упомянутых в документах;
- авторские права на фотографии, книги и сканы;
- условия использования внешних архивов и баз данных;
- право на публикацию предоставленных родственниками материалов;
- возможные ограничения доступа к архивным документам.

Публичный репозиторий означает, что его содержимое доступно всем, включая историю Git. Не размещать там конфиденциальные материалы в расчёте на то, что их можно будет скрыть ссылкой.

## 20. Локальная разработка

Типичный рабочий процесс:

1. Установить Python.
2. Создать репозиторий и локальную рабочую копию.
3. Создать виртуальное окружение.
4. Установить зависимости.
5. Запустить локальный сервер.
6. Проверить страницы и ссылки.
7. Сделать commit и push в GitHub.
8. Проверить результат сборки в GitHub Actions.

Пример команд:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

mkdocs serve
```

На Windows активация виртуального окружения отличается. Для обновления зависимостей использовать `pip install -r requirements.txt`.

Сборка сайта локально:

```bash
mkdocs build --strict
```

Готовые файлы появятся в каталоге `site/`. Этот каталог обычно не нужно коммитить в основной исходный репозиторий при использовании GitHub Actions.

## 22. Критерии готовности первой версии

Первая версия считается готовой, если:

- сайт публикуется автоматически после изменения в основной ветке;
- все страницы доступны через навигацию или внутренние ссылки;
- каждая тестовая персона имеет стабильный ID;
- источники имеют отдельные ID и описания;
- биографии содержат ссылки на соответствующие источники;
- фотографии и тестовый PDF открываются корректно;
- локальная сборка проходит без ошибок;
- отсутствуют известные битые внутренние ссылки;
- сайт читаем на мобильном устройстве;
- в публичном репозитории нет намеренно закрытых материалов и секретов.
